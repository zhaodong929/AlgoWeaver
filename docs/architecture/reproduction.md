# Reproduction planning and template artifacts

`ReproductionPlanner` converts a validated capability card and optional retrieval hits into a structured `ReproductionPlan`. The plan records objective, required inputs, expected outputs, dependencies, ordered steps, acceptance checks and evidence IDs. Missing core fields or provenance make the plan `blocked`.

`TemplateArtifactWriter` writes deterministic demo artifacts for the moving-average example. It never imports or executes the generated source, and every artifact is explicitly `unverified`. Runtime validation and promotion to a verified capability belong to the later sandbox workflow.

`ArtifactGenerator` defines the provider-neutral generation boundary used by the reproduction graph. The default `template` mode keeps the deterministic moving-average writer. `MockCodeGenerator` uses that same reviewed template while labeling the plan and artifacts as `mock`, which makes offline demonstrations distinguishable from model output. `LLMCodeGenerator` sends the evidence-linked plan and retrieval hits through the `ChatModel` protocol and validates the returned JSON with `GeneratedCodeDraft` before creating `algorithm.py` and `test_algorithm.py`. Model-declared dependencies are merged into the plan for later static analysis.

The CLI and API expose `generation_mode=template|mock|llm`. The `llm` mode requires the `litellm` provider mode explicitly; a missing provider configuration fails at the boundary instead of silently treating a mock response as generated code. All three modes produce artifacts with `verification_status="unverified"`. Static checks and isolated execution remain required before registry promotion. Current tests use a fake `ChatModel` contract, so a real provider call and general-model runtime acceptance remain open evidence items.
